# 侧聊 `/side`：创建时上下文上的独立、无工具问答

主任务继续执行时，用户可以另开一个侧聊，追问“这个工具用了什么参数”“刚读的代码是什么意思”“这次修改的依据是什么”，不用重新交代背景。侧聊**只给用户看**：它不是 Worker，不向主 Agent 汇报，不写主线历史、收件箱、工具账本或 Worker，也没有任何执行工具的途径。

实现：`src/baseagent/agent/side.py`（快照、请求构造、侧聊状态机）；接入点在 `run_agent(..., request_observer=)`、`SessionStore`（一致读、`side_attempts` 表）、`TurnBudget`、`ChatSession` 与三个前端。

## 怎么用

| 操作 | CLI | TUI | Web |
| --- | --- | --- | --- |
| 打开 / 追问 | `/side <问题>`（没有打开的侧聊就先打开） | 右栏侧聊输入框（Tab 切换焦点）；主输入框里的 `/side …` 也送到侧聊 | 右栏侧聊面板的输入框 |
| 停止正在回答的问题 | `/side-stop`；主 Agent 空闲而侧聊在答时 `Ctrl+C` | `/side-stop`（不新增快捷键，底栏不变） | “停止” |
| 重新发送已停止 / 失败的上一问 | `/side-retry`（新请求，重新计费） | `/side-retry` | “重试上一问” |
| 结束侧聊 | `/side-end`；`/exit` 退出时自动结束 | `/side-end`；退出时结束 | “结束侧聊” |
| 查看状态 | `/side` | 同左 | 面板状态 |

- 同一时间只有一个侧聊，一次只答一个问题。`/side-end` 之后再 `/side <问题>` 会按**当时**的主会话重新打开一个。
- 默认看**主会话**。`/side w1` 这类查看 Worker 内部历史的用法**没有实现**：`w1 …` 只是普通问题文字。Worker 的公开状态（id、状态、任务、汇报摘要）会出现在任务参考里。
- 侧聊只在交互对话里可用；一次性任务、`--resume`、JSON 输出没有侧聊。开了 `--preauthorize-model` / `--estimate-model` 时拒绝打开：侧聊请求没法按同样规则预留 token，所以不发送。

## 快照：创建时固定，之后不追新

打开侧聊时固定上下文：

1. **live（首选）**：主 Agent 在本进程里**最近一次成功返回的真实请求**（`run_agent` 交给适配器的投影，含中间件加的 system 消息、过滤后的工具列表），原样作为前缀；再接上这次请求之后已经提交、而且整批工具都已有结果的消息。
2. **未完成的工具批次**（执行中、等待审批、已返回但还没写进对话）**不作为工具历史发送**，而是写成一段标明来源的事实：参数原文、已完成的结果、“执行中、结果未知，约 N 秒”“等待审批，未执行”“已返回但未定稿（不展示正文）”。不伪造工具结果，也不改主历史；运行中命令的输出侧聊看不到。
3. **未了任务参考**：创建时读一次，之后**不再更新**。内容包括计划与最近检查记录、Worker 的公开状态、后台任务（只读内存中的记录：不刷新、不读盘、不取通知、不改 `notified`）、待审批调用、收件箱里还没送到主任务的内容（只看，不取走）。这部分在第一个侧聊问题里出现一次，后续追问不会重复添加。
4. **cold**：本进程还没有主任务的真实请求（例如刚重启），或主历史在那次请求之后被改写过，就把已保存的会话**文本化**放进一条用户消息，不带工具定义、工具消息和思考块。这样对所有供应商都合法，但前缀不复用；打开时会提示。

读取顺序是：先读最近请求的记录，再用**一个**只读事务读会话、工具账本和开始时间，然后读内存里的任务参考，最后再核对一次最近请求。如果这期间又有请求返回，就重读一遍（最多 5 次，之后退回 cold）。只读事务给出的是数据库的一个提交点，不等于内存里同一时刻的状态，所以事实块会标明“创建侧聊时读取（时刻）”，不宣称两者是同一时点。

**快照固定的是对话，不是工作区**：之后文件可能已经变化，侧聊回答会被要求如实说明。主任务创建侧聊之后的新结果、新消息、计划更新都**不会**进入侧聊；侧聊的问题和回答也**不会**进入主任务。

## 请求与供应商

- 首问 = 前缀 + 一条用户消息（侧聊说明 + 事实 + 问题），追问只追加侧聊自己的问答。侧聊说明放在用户消息里，不加 system 消息：Anthropic 会把 system 消息并入顶层 `system`，签名思考块随之失效。
- **工具定义照原样发送，但从不执行**：去掉工具定义会改变前缀，使 Anthropic 的签名思考块失效，而且历史里有工具块时必须定义工具。模型若在侧聊里请求工具，只显示“请求了 X，未执行”；这一问照常计费，侧聊历史里只保留文字。
- 超出 `--max-context-bytes` 时改用文本化上下文，从最早的内容开始省略并注明省略了多少条，不另调用摘要模型；仍然放不下就拒绝，并提示 `/side-end` 后重开。
- 沿用主会话的模型和生成参数（含 `--thinking` / `--effort`）。**本版不提供单独降低侧聊思考预算**：它对缓存和思考块的影响没有验证，不把“只损失消息级缓存”当作前提。
- 打开时会说明以下几点：

| 供应商 / 适配器 | 流式 | 缓存 |
| --- | --- | --- |
| OpenAI 兼容（含 DeepSeek） | 是：逐段到达；DeepSeek 思考模式的 `reasoning_content` 会保留并回传 | 由供应商自动决定，没有做真实验证 |
| Anthropic | **否**：回答完整到达后一次显示 | 适配器不发 `cache_control`，**不会命中缓存** |

## 计费与用量

- 每次侧聊请求先在 `side_attempts` 表里写一行，标为“用量未知”，**然后**才发请求；用量到达时只结算一次（之后到达的重复或冲突上报都忽略）。这张表在第一次用 `/side` 时才创建，没用过侧聊的会话库保持原样。
- 用量记到**受理这次请求时的主轮次**，主任务之后进入新一轮也一样。侧聊不占主任务和 Worker 的步数、模型调用次数；它计入这一轮共享的 `--budget-cny`。每个侧聊最多 `--max-model-calls` 次请求；设了 `--max-total-tokens` 时它也约束侧聊自己的累计 token。
- **沿用现有的未知用量规则**：一次侧聊请求没有拿到用量就结束（例如流式回答被停止、连接断开、进程崩溃），这次用量记为未知，**不按 0 计**。设了 `--budget-cny` 时，这一轮的共享池会拒绝继续花费，**主任务这一轮的下一次模型调用也会停下**（`max_tokens_exceeded`，原因 `budget_cny`），和 Worker 用量未知时完全一样；新的一轮有自己的池，不受影响。没设 `--budget-cny` 时不会拦截。在途请求不算未知。
- 晚到的用量（例如 Anthropic 的整条回答在停止之后才返回）照样记到原来那一次请求和原来那一轮；已经显示过的部分保留，晚到的正文不再作为回答显示。
- 重启后能从库里重建每轮的花费：主 Agent、Worker 和侧聊的用量都算进去，未知的仍是未知（`seed_turn_usage`）。

## 停止、结束、关闭视图与重连

- 停止和结束**只作用于侧聊**，不取消主任务、Worker、后台任务或命令。打断主线等待、放弃目标、停止进程仍各走原来的入口（`Ctrl+C` 取消主回合、`/cancel`、`job_kill`）。
- 流式请求停止时会关闭连接；整条请求无法中途打断，停止只是不再显示，用量到达后照常结算。
- 侧聊内容**只在本进程内存里**：退出时侧聊结束，并打印已发生的请求数和用量。进程崩溃或重启后，侧聊不能接着聊；下次进入同一会话时会说明“上次进程里的侧聊已随进程结束”，以及记录到的用量和未知次数。
- Web：关闭页面**不会**停止侧聊，请求会照常完成并计费；停止或结束请用面板按钮。TUI 退出即结束侧聊。
- 重连只恢复显示：侧聊有自己的事件缓冲和 SSE（`/side/events`），断线后按 `Last-Event-ID` 补发，或用 `resync` 快照重建面板，**不会**重新发出请求。每次提交都带 `op_id`，同一个 `op_id` 只受理一次，进程重启后也一样（记录在库里）。显式重试是新的 `op_id`、新的一次请求、单独计费。

## 事件（侧聊自己的缓冲）

| 类型 | 字段 | 何时 |
| --- | --- | --- |
| `side_opened` | side, origin, mode, turn, taken_at, notes, streams | 打开侧聊，快照已固定 |
| `side_question` | side, attempt, op_id, text, turn | 问题被受理，请求正在发送 |
| `side_delta` | side, attempt, offset, text | 回答的一段到达；offset 是此前已发出的字符数，重放时不重复追加 |
| `side_answer` | side, attempt, status, text | 回答完成（completed 或 tool_requested） |
| `side_stopped` / `side_failed` | side, attempt, text（, error） | 用户停止 / 请求失败；text 是已显示的部分 |
| `side_usage` | side, attempt, late, usage, prompt_tokens?, completion_tokens? | 用量已知（reported）或不会再来（unknown）；late 表示在停止之后到达 |
| `side_notice` | side, text | 说明或拒绝 |
| `side_ended` | side, attempts, prompt_tokens, completion_tokens, unknown, pending, stopped | 侧聊结束 |

Web 接口：`GET /side`、`GET /side/events`（SSE）、`POST /side/messages {"text","op_id"}`、`POST /side/retry {"op_id"}`、`POST /side/stop`、`POST /side/end`。主线的 `/events` 不包含侧聊事件。

## 已知限制

- 主线的一个现有问题（侧聊不会新增它，但会继承）：走 Anthropic 时，只要有一条工具结果超过 `--max-tool-context-bytes`（默认 4000 字节），`ContextPolicy` 就会插入一条 system 提示。适配器把它并入顶层 `system`，此前的签名思考块随之不再匹配。按官方文档，`claude-opus-5-5` 上这种情况**可能**返回 400。侧聊自己追加的内容不加 system 消息。
- 每次请求的 CNY 按现有的固定费率估算（与 `--budget-cny` 相同），换模型时金额不准。
- 侧聊对话不持久化，不提供多侧聊管理，不实时刷新，不回写主线，不升级工具权限。
